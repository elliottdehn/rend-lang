01 — The wedge

What rend gives you that SQL + ORM can't.

Three structural properties that aren't a configuration knob — they're how the language is shaped.

  • Parallel ACID. Actually.

    Write a batch of operations and have them run concurrently inside one serializable transaction. SQL gives you ACID or parallelism — never both, because multi-statement parallelism requires splitting into multiple txns, which breaks atomicity across the batch. rend's parallel for runs statements in shadow transactions that merge in stable order with conflict re-run. Outside observers see one txn; inside, the work fans out across cores.

  • Bugs the parser refuses.

    Sticky-typed boundaries — declare a parameter as `string` and the type system rejects every call site that tries to pass a computed value. The SQL-injection class of bug isn't patrolled at runtime — it's structurally absent at the API surface. The same property propagates through struct fields, array elements, and let-bindings; the safety lives in the type signature, not the code review.

  • Never think about sharding.

    Keys hash automatically across the cluster; cross-shard transactions are transparent; no partition keys to pick, no consistent-hashing config, no manual rebalancing. Built atop FoundationDB — the same storage layer Apple uses for iCloud and Snowflake uses for metadata. You inherit a decade of deterministic-simulation testing and the resolver model for cross-shard atomic commits. From rend's side, it's all one ACID database.

02 — What it feels like

A request handler, in two layers.

A rend program has a module — the durable schema and reusable helpers, evolved in source — and main — the per-request transaction, synthesized fresh by the JIT-codegen layer from each incoming payload.

The module  ·  durable, deployed once

module strdedup;

struct Entry { id: u64, created: u64 }

state forward: pmap<string, Entry>;
state by_id:   pbtree<u64, string>;
state next_id: u64;

unique_index by_id on forward.(id ASC);

struct InternResult { id: u64, fresh: bool }
const DAY_MS: u64 = 86400000u64;

fn intern_at(s: `string`, slot: u64) -> InternResult {
    let existing = forward[s];
    if existing.id > 0u64 {
        return InternResult { id: existing.id, fresh: false };
    }
    forward[s] = Entry { id: slot, created: block_timestamp() };
    return InternResult { id: slot, fresh: true };
}

entry fn intern_batch(strings: `[string]`) -> [InternResult] {
    let n       = len(strings);
    let slots   = reserve n from next_id;
    let results = arr<InternResult>[n];

    parallel for (i, s) in strings to results {
        intern_at(s, slots[i])
    }

    // 2-stale-row GC per fresh insert, in one sweep after the merge.
    let fresh = 0u64;
    for r in results {
        if r.fresh { fresh = fresh + 1u64; }
    }
    let now    = block_timestamp();
    let cutoff = if now > DAY_MS { now - DAY_MS } else { 0u64 };
    for old in by_id limit fresh * 2u64 {
        if forward[old].created >= cutoff { break; }
        delete forward[old];
    }

    return results;
}

The transaction  ·  per-request, JIT-synthesized

fn main() -> [InternResult] {
    return intern_batch(`["alpha", "beta", "gamma", "delta"]`);
}
03 — What you escape

The same thing in PL/pgSQL.

A working Postgres implementation of the same batch-dedup-with-GC operation. The structural costs aren't a style choice; they're how PL/pgSQL is shaped.

CREATE TABLE strings (
    id          BIGSERIAL PRIMARY KEY,
    content     TEXT NOT NULL UNIQUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_strings_created ON strings (created_at);

CREATE OR REPLACE FUNCTION intern_batch(inputs TEXT[])
RETURNS TABLE (id BIGINT, fresh BOOLEAN)
LANGUAGE plpgsql AS $$
DECLARE
    s        TEXT;
    new_id   BIGINT;
    found_id BIGINT;
    cutoff   TIMESTAMPTZ;
BEGIN
    cutoff := NOW() - INTERVAL '24 hours';
    FOREACH s IN ARRAY inputs LOOP
        INSERT INTO strings (content) VALUES (s)
        ON CONFLICT (content) DO NOTHING
        RETURNING strings.id INTO new_id;

        IF new_id IS NOT NULL THEN
            found_id := new_id;
            fresh := TRUE;
            new_id := NULL;
            DELETE FROM strings WHERE id IN (
                SELECT id FROM strings
                WHERE created_at < cutoff
                ORDER BY id ASC LIMIT 2
            );
        ELSE
            SELECT strings.id INTO found_id
            FROM strings WHERE content = s;
            fresh := FALSE;
        END IF;
        id := found_id; RETURN NEXT;
    END LOOP;
END;
$$;
  • Every INSERT pays a sequence advance. BIGSERIAL is one global hot atomic cell every concurrent writer queues against. rend's reserve N from next_id does one bump per batch and hands the ids to N parallel legs.
  • Decomposition isn't available. PL/pgSQL has no module-level public/private; calling another function carries the subtransaction tax. Real procedures grow into monolithic blocks. rend factors into helper / stable entry / one-line main.
  • Serial by construction. FOREACH runs one row at a time. Parallelism requires multiple connections, which means multiple transactions, which breaks atomicity across the batch.
  • GC and dedup share lock paths. The unique-on-content INSERT and the DELETE both touch the strings table's indexes. Concurrent batches deadlock on logically-disjoint writes; the app retries serialization failures.
  • Schema lives in migration files. Every change adds another NNNN_xyz.sql file the codebase carries forever. You can never look at a single file and know what's deployed. rend's source IS the schema.
  • User input flows in as untagged TEXT[]. Nothing in the type signature distinguishes a literal payload from a string the app built by concatenation. SQL-injection is a property of the API surface, not absent by construction.
04 — Built for

Workloads where wrong has a number attached.

rend is shaped for the kind of systems where "eventually correct" isn't an answer.

Financial rails

Idempotent transfers with structurally-enforced request-id dedup. Retry the same transaction id, get the recorded outcome — no double-debit, no app-side retry-loop, no eventual-consistency hand-waving.

Audit-mandated systems

Current-state schema lives in your source tree, not a migration pile. Untagged user input can't reach a typed parameter. Auditors read code, not migration archeology.

Multi-tenant SaaS

Hash sharding handles tenants of any size. No shard-key picking, no cross-tenant query coordination, no "we'll deal with sharding at Series B."
