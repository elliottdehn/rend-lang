The wedge

What an application backend can't be when its kernel is SQL — and what it becomes when its kernel is a real programming language.

  • Parallel ACID, actually

    SQL gives you ACID inside a transaction but serializes the body. Real multi-statement parallelism requires multiple transactions, which breaks atomicity across the batch. rend's parallel { } and parallel for ... to run multiple writes concurrently inside one transaction — each statement in its own shadow Tx, deltas merged in stable order with OCC conflict re-run. Outside observers see a single serializable txn.

  • The language is the spec

    Schema lives in source, not a pile of migration files. The compiler diffs declarations against the deployed ledger and applies additive changes automatically; transforming changes require an explicit migration block that runs exactly once at version bump and can be deleted from source afterward. You always know what the current contract is by reading the code — no external schema viewer required.

  • Audit-grade by construction

    Explicit literals — `<value>` — are a parse-time guarantee that no code can hide in a value. Sticky typing propagates the constraint through API boundaries, so a function declaring name: `string` rejects any call site that passes computed data. The class of bug that ships SQL injections past code review is structurally absent — not patrolled, absent.

  • Stored procedures, but a real language

    PL/pgSQL has variables, control flow, and exceptions — the surface shape of a language — but no module system, an anemic type system, exception handling that allocates per-call subtransactions you can't see in the source, debugging by RAISE NOTICE and tail -f, and version control through migration files instead of code. rend's entry fn sits next to the data because the data IS in the language's value space — no DSL bolted onto SQL, no category confusion.

What it feels like

A rend program has two layers: the module — the durable schema and the helper logic, deployed once — and main — the per-request transaction, synthesized fresh by the JIT-codegen layer from each incoming payload.

The module   — durable, deployed once

Schema, structs, private helpers, and the stable entry functions that form the module's API. Lives in source; the runtime ledger tracks what's actually deployed.

module strdedup;

state forward: pmap<string, u64>;   // content → id (HAMT-disjoint per key)
state reverse: pmap<u64, string>;   // id → content
state created: pmap<u64, u64>;      // id → insert timestamp (ms)
state ids:     pbtree<u64, u64>;    // sorted-id index for the GC walk
state next_id: u64;                 // sole intentionally-contended cell

struct InternResult { id: u64, fresh: bool }

const DAY_MS: u64 = 86400000u64;

// Private helper. One read on a dedup hit; two writes + an
// opportunistic GC sweep on a miss. The slot is caller-supplied,
// so this function never contends on `next_id`. `s: `string`` is
// sticky — any caller must supply a backtick-tagged value;
// computed strings are a typeck error.
fn intern_at(s: `string`, slot: u64) -> InternResult {
    let existing = forward[s];
    if existing > 0u64 {
        return InternResult { id: existing, fresh: false };
    }
    let now = block_timestamp();
    forward[s] = slot;
    reverse[slot] = s;
    created[slot] = now;
    ids[slot] = slot;

    // GC: drop up to 2 stale entries (>24h old), ascending by id.
    // ids are assigned monotonically, so `created[id]` is non-
    // decreasing in id — the walk stops at the first non-stale.
    let cutoff = if now > DAY_MS { now - DAY_MS } else { 0u64 };
    let removed = 0u64;
    for old_id in ids {
        if removed >= 2u64 { break; }
        if old_id == slot { break; }
        if created[old_id] >= cutoff { break; }
        let old_str = reverse[old_id];
        delete forward[old_str];
        delete reverse[old_id];
        delete created[old_id];
        delete ids[old_id];
        removed = removed + 1u64;
    }
    return InternResult { id: slot, fresh: true };
}

// The stable API. The signature is what the JIT-codegen layer
// generates against, what clients call, and what every `main`
// the synthesizer emits is a thin wrapper over. `strings:
// `[string]`` means the payload must arrive as inert data —
// the safety property propagates outward from this signature
// through every call site, no matter how many hops.
entry fn intern_batch(strings: `[string]`) -> [InternResult] {
    let n       = len(strings);
    let slots   = reserve n from next_id;
    let results = arr<InternResult>[n];

    parallel for (i, s) in strings to results {
        intern_at(s, slots[i])
    }

    return results;
}

The transaction   — per-request, JIT-synthesized

Each request gets its own main emitted by the JIT-codegen layer from the incoming payload. The payload is embedded as an explicit literal so the parser refuses any code-shaped fragment; the body is a one-line call into the stable module entry. Everything substantive — atomic id reservation, the parallel-for fan-out, the shadow-Tx merge, the conflict re-run — lives behind the entry's signature, so it stays the same whether the call comes from a client SDK or a synthesized main.

fn main() -> [InternResult] {
    return intern_batch(`["alpha", "beta", "gamma", "delta"]`);
}

The same thing in SQL

For comparison: a Postgres / Supabase implementation of the same batch-dedup operation. Schema lives in a migration file; the logic lives in a PL/pgSQL stored procedure; the app calls it via PostgREST RPC.

The schema   — migrations/0001_create_strings.sql + 0002_add_created_at.sql

CREATE TABLE strings (
    id          BIGSERIAL PRIMARY KEY,
    content     TEXT NOT NULL UNIQUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_strings_created ON strings (created_at);

The stored procedure   — database/functions/intern_batch.sql

CREATE OR REPLACE FUNCTION intern_batch(inputs TEXT[])
RETURNS TABLE (id BIGINT, fresh BOOLEAN)
LANGUAGE plpgsql AS $$
DECLARE
    s        TEXT;
    new_id   BIGINT;
    found_id BIGINT;
    cutoff   TIMESTAMPTZ;
BEGIN
    cutoff := NOW() - INTERVAL '24 hours';
    FOREACH s IN ARRAY inputs LOOP
        -- Try INSERT first. ON CONFLICT DO NOTHING returns no row
        -- on a duplicate, so `new_id` stays NULL — that's the only
        -- signal we have to distinguish a fresh insert from a hit.
        INSERT INTO strings (content) VALUES (s)
        ON CONFLICT (content) DO NOTHING
        RETURNING strings.id INTO new_id;

        IF new_id IS NOT NULL THEN
            found_id := new_id;
            fresh := TRUE;
            new_id := NULL;

            -- GC on each fresh insert: drop up to 2 oldest stale rows.
            -- Subquery picks the candidates by ascending id; the outer
            -- DELETE removes them. The unique-on-content INSERT above
            -- and this DELETE share a row-lock path against the unique
            -- index — under concurrent batches you'll see lock-ordering
            -- waits, and the app retries serialization failures.
            DELETE FROM strings
            WHERE id IN (
                SELECT id FROM strings
                WHERE created_at < cutoff
                ORDER BY id ASC
                LIMIT 2
            );
        ELSE
            -- Duplicate — fall back to SELECT to find the existing id.
            SELECT strings.id INTO found_id
            FROM strings WHERE content = s;
            fresh := FALSE;
        END IF;

        id := found_id;
        RETURN NEXT;
    END LOOP;
END;
$$;

Pain points the rend version doesn't inherit:

  • Decomposition isn't available. The rend version factors into a private intern_at, a stable entry fn intern_batch, and a one-line main. PL/pgSQL has no module-level public/private distinction; functions can call other functions but doing so commits you to either the subtransaction tax (via EXCEPTION) or the RAISE-aborts-the-caller trap. Real procedures grow into dense monolithic blocks because the language doesn't give you the primitives to split them. The density you see here isn't a presentation choice — it's how the code looks in production.
  • Serial by construction. The FOREACH loop runs one string at a time. To parallelize you'd call the function from multiple app connections, each with its own transaction — which breaks atomicity across the batch.
  • The GC and the dedup share lock paths. The unique-on-content INSERT and the DELETE both touch the strings table's indexes. Two batches running concurrently can deadlock on the same rows even though the writes are logically disjoint; the app sees a serialization-failure exception and retries. The rend version's GC writes (forward / reverse / created / ids) are HAMT/pbtree-disjoint per id, so concurrent GCs of different ids commute under OCC merge with no lock dance.
  • Exception handling has a tax. Using EXCEPTION WHEN unique_violation instead of the CTE-UNION pattern would allocate a subtransaction per loop iteration. The CTE pattern is the canonical workaround.
  • PL/pgSQL is a DSL bolted onto SQL. Anemic types, no module system, no real composability, debugging by RAISE NOTICE, tests run inside the database. The surface looks like programming but every property of the tool fights you.
  • Schema lives in migration files. Every change adds another NNNN_xyz.sql file the codebase carries forever. You can never look at a single file and know what the current schema is — you need external tooling to introspect the live database.
  • User input flows in as untagged TEXT[]. Nothing in the type signature distinguishes a literal payload value from a string the application built by concatenation. The SQL-injection class of bug is a property of the API surface, not absent by construction.

What it isn't

rend is the durable kernel. There is no built-in auth dashboard, no realtime websocket layer, no blob storage, no admin UI. Those are engineering on top of a substrate — and the substrate is the part that's structurally hard.

What you get: ACID transactions that actually parallelize, a language that composes the way languages do, and a type system that catches the class of bug the alternatives ship past code review.

What you provide: HTTP, auth, realtime, dashboards. These ride on top of any reasonable application layer and don't need to live in the kernel.
